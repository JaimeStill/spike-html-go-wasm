spike-html-go-wasm

A spike for the Standards Lab reference architecture: workspace Go run live in the browser through GOOS=js WebAssembly, on this GitHub Pages project site. Its answer is evidence for whether v1.repository-docs and the Pages sites embed live Go demos; the spike decides nothing itself.

The runtime page runs hello and the probe's handlers in a worker, loading Go only on a Run.

The question

Can a page run workspace Go live in the browser through GOOS=js WebAssembly (library demos, service handlers called in-process, and a general Go playground that compiles arbitrary Go in the page) with acceptable capability and performance? Sizes are measured and reported, not held to a budget.

The evidence

  1. Workspace Go by published tag, built by standard Go for GOOS=js in the check and the Pages workflow; no committed .wasm.
  2. A live sqlate page under /<repo>/: edit a statement, see its compiled SQL with $n placeholders and its compile errors.
  3. A statement run in-process over sqltest's scripted driver, with no socket.
  4. Each module's raw, gzip-as-Pages-serves, and brotli-11 bytes, with a TinyGo comparison build.
  5. Cold-load cost on the live site: the page readable before the module, time to first result after the click, and cold, cached, and in-place-switch timings.
  6. wasm_exec.js copied from the pinned toolchain with provenance; .wasm served as application/wasm.
  7. The screenshot review, every palette's editor included, leaving no capture file; Firefox and Safari where available.
  8. The verdict for v1.repository-docs and the Pages sites.
  9. A playground where the reader edits and runs arbitrary Go in the page, with load, compile, link, and run timings.
  10. The go-core graph and go-web-sdk demos live, their sizes reported.
  11. The bridge, the runtime, and sl-go-demo used unchanged by every scenario, embedded in a rendered Markdown page and in a hand page.
  12. The four programs (basics, generics, concurrency, standard library) edited and run in the page.
